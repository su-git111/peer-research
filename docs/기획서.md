# Cowork 서비스 기획서

> 자율 AI 연구 동료 에이전트 · 서비스 기획 문서
> 작성 관점: "AI Agent 서비스 기획" — 문제 정의부터 에이전트 설계·확장 비전까지

---

## 0. 한 줄 정의

**Cowork는 연구자의 하루를 계획하고, 자는 동안 계산과 자료조사를 대신 진행시켜 아침 리포트로 남기는 자율 AI 연구 동료다.**

North Star: *"연구자가 자리에 없는 동안 에이전트가 대신 완료한 유효 작업의 수."*

---

## 1. 문제 정의 (Problem)

### 1.1 연구 업무의 구조적 특성
생명정보학·데이터 연구자의 하루는 다른 지식노동과 다르다.

- **긴 대기시간** — 클러스터링, 파라미터 스윕, 시뮬레이션 등 한 번 돌리면 수십 분~수 시간. 그 사이 사람은 놀거나 컨텍스트를 잃는다.
- **멀티 프로젝트 병렬** — 보통 2~4개 프로젝트가 서로 다른 단계에서 동시 진행. 우선순위가 매일 흔들린다.
- **파편화된 기록** — 결과는 노트북·슬랙·메모·머릿속에 흩어지고, 회고와 포트폴리오는 "나중에"로 미뤄진다.
- **자료 추적 부담** — 관련 논문·툴 업데이트가 매일 쏟아지지만 따라잡을 시간이 없다.

### 1.2 페인포인트
| # | 페인포인트 | 결과 |
|---|-----------|------|
| P1 | 계산이 도는 밤·빈 시간을 활용하지 못함 | 실질 연구 시간 손실 |
| P2 | 매일 "뭐부터 하지"에 인지 비용 소모 | 착수 지연, 중요한 일 누락 |
| P3 | 한 일을 기록·회고하지 않음 | 진행보고·포트폴리오·논문 작성 때 재고생 |
| P4 | 관련 연구를 놓침 | 중복 연구, 뒤늦은 방법 발견 |

### 1.3 기존 도구의 한계
- **Notion·Todoist (수동 관리)** — 계획을 대신 세우거나 실행하지 않는다. 입력·유지 자체가 일.
- **ChatGPT·Claude 챗 (비자율)** — 세션이 끝나면 기억이 없고, 스스로 시간에 맞춰 움직이지 않으며, 긴 작업을 대신 돌리지 못한다.
- **코딩 에이전트 (Cursor 등)** — 코드 작성엔 강하지만 연구 업무 전반의 계획·기록·자료조사를 다루지 않는다.

> **인사이트:** 연구의 병목은 아이디어가 아니라 *긴 대기시간과 파편화된 실행·기록*이다. 이건 더 나은 "입력 도구"가 아니라, **시간에 따라 스스로 움직이고 도구를 직접 다루는 에이전트**로만 풀린다.

## 2. 타겟 유저 & 페르소나

### 2.1 타겟 세그먼트
- **1차:** 생명정보학·계산과학 대학원생/포닥 (파이프라인·스크립트 기반 워크플로, 긴 잡, 멀티 프로젝트)
- **2차:** 데이터사이언스·ML 연구자, 실험+분석 병행 연구자
- **확장:** 연구실 단위 팀, R&D 조직

### 2.2 페르소나
**김서연 · 생명정보학 석박통합 3년차**
- 상황: CellCharter 기반 공간전사체 분석 프로젝트 2개 + 협업 1개. 밤에 파라미터 스윕을 돌려놓고 자주 잊는다.
- 니즈: "자는 동안 계산이 끝나 있고, 아침에 뭘 할지 정리돼 있으면 좋겠다."
- 페인: 매일 아침 우선순위 재설정에 30분, 랩미팅 전날 밤 "이번 주 뭐 했지" 재구성, 관련 논문 놓침.
- 성공 정의: 아침에 켰을 때 **밤새 계산 결과 + 관련 논문 + 오늘 할 일**이 정리돼 있는 것.

## 3. 서비스 컨셉 & 가치 제안

### 3.1 컨셉
**"24시간 함께 일하는 연구 동료."** 낮에는 계획·기록을 돕고, 밤에는 대신 일한다.

### 3.2 핵심 가치 제안 (하루의 변화)
| | Before | After (Cowork) |
|---|--------|----------------|
| 아침 | "오늘 뭐부터 하지" 30분 고민 | 오전/오후/밤 체크리스트 + 밤샘 결과가 준비됨 |
| 낮 | 계산 돌려놓고 대기, 컨텍스트 손실 | 진행률 대시보드로 프로젝트 상태 한눈에 |
| 밤 | 계산 켜놓고 잠, 논문 못 따라감 | 에이전트가 계산 실행·모니터링 + 논문 스캔 |
| 주간 | "이번 주 뭐 했지" 재구성 | 자동 회고 + 포트폴리오 축적 완료 |

### 3.3 왜 에이전트여야 하는가 (설계 원칙)
1. **자율성 (Autonomy)** — 스케줄 기반으로 사람 없이 계획·실행.
2. **지속성 (Persistence)** — 마크다운 상태 저장으로 세션을 넘어 기억.
3. **도구 사용 (Tool use)** — 셸·웹·파일을 직접 다뤄 실제 작업 진행.
4. **신뢰 (Trust)** — 자율성엔 가드레일이 필수. 위험 행동 차단 + 사람 확인 지점.

## 4. 기능 정의 (Features)

각 기능은 유저스토리 → 동작으로 기술한다.

### F1. 주간 계획 `/weekly`
- *유저스토리:* "월요일 아침, 지난주에 뭘 했고 이번 주에 뭘 할지 자동으로 정리돼 있으면 좋겠다."
- 동작: 지난주 일간 기록에서 완료/미완을 자동 집계해 회고 작성 → 프로젝트 목표를 보고 이번 주 Top 3 + 프로젝트별 할 일 제안.

### F2. 일간 체크리스트 `/daily`
- *유저스토리:* "하루를 오전·오후·밤으로 나눠 뭘 할지 정해주고, 어제 못 한 건 넘겨줘."
- 동작: 주간 계획·프로젝트를 읽고 어제 미완을 이월 → 오전/오후/밤 3구간 배치(실험 대기·마감·blocker 우선 고려).

### F3. 야간 근무 `/night` ★ 핵심 차별 기능
- *유저스토리:* "자는 동안 계산을 돌려주고, 관련 논문도 찾아서 아침에 정리해줘."
- 동작:
  1. `night/queue.md`의 대기 명령을 실행·모니터링(백그라운드 + 로그).
  2. `night/watchlist.md` 키워드로 최근 논문·툴 업데이트 웹 검색·요약.
  3. `night/reports/`에 아침 리포트 생성(계산 결과 + 논문 + 아침 액션 제안).
- 안전: 파괴적 명령 차단, 웹 내용은 데이터로만 취급, 사람 확인 필요 항목 별도 표시.

### F4. 포트폴리오 자동 축적 `/close`
- *유저스토리:* "오늘 한 일을 나중에 보고서·포트폴리오로 쓰게 남겨줘."
- 동작: 완료 항목을 산출물·수치·배운 점과 함께 월별 업무일지로 누적.

### F5. 대시보드
- *유저스토리:* "지금 상태를 한 화면에서 보고 싶다."
- 동작: 프로젝트 진행률(작은 목표 체크박스 기반) + 이번 주 + 오늘 3구간 + 지난 밤 리포트. 라이트/다크.

## 6. 에이전트 설계 관점 (요약)

Cowork는 단일 프롬프트가 아니라 **4개의 워크플로(스킬)로 분해된 에이전트**다. 각 워크플로는 자기완결적 지시(도구·출력·안전규칙 포함)를 갖고, 로컬 스케줄러가 시간에 맞춰 트리거한다. 상태는 마크다운 파일이 단일 소스(source of truth)이고 대시보드는 파생 뷰다.

→ 상세: **[architecture.md](architecture.md)** (시스템 구조, 오케스트레이션, 스케줄링, 안전 설계, 데이터 모델, 트레이드오프).

## 7. 안전·신뢰 설계 (Responsible Agent)

자율 실행은 강력한 만큼 오작동·오남용 리스크가 크다. 세 층위로 방어한다.

| 리스크 | 가드레일 |
|--------|---------|
| 자율 실행 중 파괴적 명령 | 삭제·전송·게시·자격증명 입력 포함 명령은 실행하지 않고 '보류' 표시. 사용자가 큐에 직접 넣은 명령만 실행. |
| 웹 콘텐츠발 프롬프트 인젝션 | 검색·페이지 내용은 데이터로만 취급, 안의 지시는 무시하고 요약만. |
| 잘못된 자율 판단 | 되돌릴 수 없는 결정은 아침 리포트 '확인 필요(HITL)'로 사용자에게 위임. |
| 데이터 종속·잠금 | 플레인 마크다운 저장 → 언제든 이식·백업·버전관리 가능. |

## 8. 성공 지표 (Metrics)

- **North Star:** 주간 "에이전트가 자율로 완료한 유효 작업 수"(야간 계산 완료 + 채택된 논문 발견 + 이월 없이 마감된 체크리스트).
- **활성화(Activation):** 첫 주 내 `/weekly`+`/daily`+야간 큐 1건 이상 사용률.
- **리텐션(Retention):** 주간 활성(WAU), 4주 잔존율.
- **자율성 비율:** 전체 완료 작업 중 사람 개입 없이 완료된 비율.
- **신뢰(Trust):** '보류'/HITL 항목이 실제로 안전하게 처리된 비율, 오탐/미탐 건수.

## 10. 리스크 & 오픈 이슈

- **상시 실행 제약** — 로컬 스케줄러는 앱·PC가 켜져 있어야 발화. → 클라우드 실행이 Next의 최우선.
- **계산 환경 다양성** — 사용자마다 스크립트·클러스터가 달라 큐 실행의 일반화 필요(어댑터/레시피).
- **자율성-신뢰 균형** — 자동화 범위를 넓힐수록 HITL 설계와 감사 로그가 중요.
- **논문 요약 품질** — 출처 신뢰도·최신성 검증, 환각 방지 위한 링크 필수화.
